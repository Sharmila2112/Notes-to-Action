Build a full-stack web app called "Notes to Action" that turns messy meeting notes into a clean task list, with a live "How it works" diagram that records each run and can replay it.

Before writing any code, give me a plan covering the pages, the database tables, the API routes, the list of steps in one run, and the event format. Wait for my approval before building.

WHAT THE APP DOES
- A visitor pastes messy notes (meeting notes, a to-do dump, a voice transcript) into a text box and clicks "Extract tasks".
- The server sends the notes to an AI model, which returns a JSON list of tasks. Each task has: title, owner (or "unassigned"), due date (or null), and priority (low, medium, high).
- The tasks are saved to the database and shown in a table. Visitors can mark a task done.
- Each extraction is saved as a "run" that can be viewed later from a Runs list.

ARCHITECTURE (keep these three layers separate)
- Page: the browser UI (React or plain HTML/JS, your choice). It shows the input, the task table, and the diagram.
- Server: a Node/Express (or similar) backend on Replit with API routes such as POST /api/runs, GET /api/runs, GET /api/runs/:id, GET /api/runs/:id/events, PATCH /api/tasks/:id.
- Database: Replit's built-in PostgreSQL. Tables: runs (id, input_text, status, started_at, finished_at), run_events (id, run_id, step, status, timestamp, duration_ms, detail), tasks (id, run_id, title, owner, due_date, priority, done).
- Outside service: the AI model API. Read the key from a Replit secret named AI_API_KEY. Never hard-code it.

THE STEPS OF ONE RUN (use exactly these names; they are both the server events and the diagram boxes)
1. receive_input: the server gets the notes and checks they are not empty and are under 10,000 characters.
2. create_run: a row is written to the runs table with status "running".
3. call_model: the server calls the AI model and asks for JSON only.
4. parse_output: the server parses the JSON and checks each task has a title and a valid priority.
5. save_tasks: the valid tasks are written to the tasks table.
6. finish_run: the run status is set to "succeeded" or "failed".

Every step must write an event to run_events when it starts and when it finishes or fails. Each event records the step name, the status (started, succeeded, failed, retrying), the timestamp, the duration in ms, and a short human-readable detail, such as "Found 4 tasks" or "Model returned invalid JSON".

FAILURE HANDLING (this matters most)
- If the model call times out (set a 20-second timeout) or returns an error, retry once with a short wait. Record the failed attempt as a "failed" event and the retry as a "retrying" event.
- If parse_output finds invalid JSON, retry the model call once with a stricter prompt. If that also fails, fall back to a simple rule-based extractor that treats each line starting with "-", "*", "TODO", or "[ ]" as a task. Record the fallback in the events so the diagram shows it.
- Add a "Simulate failures" checkbox on the input form. When it is on, the server makes the model call fail on the first attempt about half the time, so visitors can see recovery happen in a real run. The failures must come from the real code path, not from a fake event.
- Never lose the user's input. If the run fails completely, keep the notes on screen with a clear message and a "Try again" button.

THE "HOW IT WORKS" DIAGRAM
- Show the six steps as boxes in order, connected by arrows, with the three layers (Page, Server, Database, Outside service) labeled on each box.
- For each box show its status color, its duration in ms, and its detail text.
- When a run is viewed, the diagram loads the events from GET /api/runs/:id/events and fills in each box as its events arrive. Poll every second while the run status is "running".
- Add a Replay button. Replay reads the stored events for that run and animates the boxes in their original order at a chosen speed (0.5x, 1x, 2x). Replay must not add any delay to the real run. The timings shown must be the real durations.
- Show a clear error style (red border) on any box whose status is failed, and show the retry or fallback step next to it.

PAGES
- Home: the input form, the Simulate failures checkbox, and the "Extract tasks" button. After a run, show the diagram and task table on the same page.
- Runs: a list of past runs with date, status, and task count. Each row links to its diagram and replay.

MOBILE
- Test at a 375px-wide viewport. The diagram steps must stack vertically, the labels must stay readable, and the task table must scroll sideways inside its own container instead of the whole page.
